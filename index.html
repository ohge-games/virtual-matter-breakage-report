Where Virtual Matter Breaks

I spent one long session building a full multiplayer survival game, Ashlight, on a live Virtual Matter world, then deliberately pushed the engine until it failed. This report gives the Who, What, When, Where and Why for each breakage, plus impact, a repro and a suggested fix. Every number comes from the live server or the connected client.

Summary

The engine degraded gracefully under most direct load: rays, RPCs, tiny edits and big memory. It broke in four ways. Each one either caps how big a shared world can get or loses data without telling anyone:

  • Server-driven characters are expensive. The SDK character controller costs about 0.3 ms per NPC per frame, so roughly 40 rigged NPCs take a 60 fps server down to 13 fps.
  • Object creation stalls the whole server. Adding 200 voxel objects in one step froze the server for 1.7 s and dropped it to 9.7 fps.
  • Nothing has a ceiling. Networked state, the Lua heap and client particles all accept unlimited input until a player feels it. Networked state took 256 MB and gave a 3.6 s ping; the Lua heap reached 3 GB; the particle flood hit 8,000 against a documented 500.
  • State can silently diverge or disappear. Hot reload orphans async work, sync overwrote a newer local save, a client lost collision that the server still had, and imagine() jobs stall forever with no error.

The 5Ws, per breakage

B1

Server NPC capacity tops out near 40

CriticalWhy: measured
Who
Every player on a world that runs server-side enemies or companions. It hits any maker who uses the SDK's Examples/Character Controller.lua for NPCs, as the skills docs recommend.
What
Server fps fell from 59.8 to 41.5 at 10 rigged NPCs, 30.4 at 20 and 13.2 at 40. Spawning 20 at once blocked the server for 8.2 s in a single frame. Spawned one at a time, the worst single spawn still took 675 ms.
When
Steady state, not just at spawn. Forty NPCs held 13.2 fps for as long as they lived.
Where
Character Controller:updateControls() on the server: its capsule overlap via Collision GetOverlap. Spawn cost comes from creating about 11 streamed objects per segmented rig.
Why
A benchmark put one updateControls call at 299 µs. Forty NPCs call it every frame, which is 12 ms of a 16.7 ms budget before any AI runs. The profiler showed the NPC script at 28.6 ms per frame for 40 instances.

Impact

A world can't hold the 30–60 server-driven enemies a survival or MMO-style game expects. I capped Ashlight at 24 and throttled distant NPCs to 5 Hz movement. That lifted 40 NPCs to 27.1 fps and 24 NPCs to 36.2 fps.

Repro

-- spawn N CC characters, then:
Scene:SetProfileScriptsUpdate(true)
local t0 = AE:GetDebugTime()
for i=1,50 do cc:updateControls(Vec3(0.1,0,0), false) end
return (AE:GetDebugTime()-t0)*1e6/50  -- ≈299 µs

Suggested fix

Move the server capsule sweep into native code, or batch it across characters per frame. Add a built-in movement LOD so characters far from every client step at a lower rate. Document a per-NPC budget in the character-controller skill.

B2

Creating voxel objects stalls the whole server

CriticalWhy: inferred
Who
All connected players during any burst of object creation: spawning waves, building, debris, rig assembly.
What
I added objects (one VoxelData plus a 0.3 m sphere each) in steps. Going from 200 to 400 in one step took 1,658 ms and dropped the server to 9.7 fps average and 0.2 fps minimum. Even the 100-object steps hit a 0.5 fps minimum. Afterwards, steady-state cost also grows with count: +300 objects ran at 54.8 fps and +1,000 at 36.9 fps.
When
At creation (the spike), then in proportion to live object count.
Where
Scene:CreateObject + AddComponent("VoxelData") + the first Vox:Add(...):Force(obj), plus per-object streaming to clients.
Why
Creation work appears to run synchronously on the main thread with no per-frame budget. The edit guard throttles voxel volume but not object count. The steady-state cost points to per-object streaming and transform bookkeeping.

Impact

Segmented characters multiply the problem: each Ashlight rig is about 11 objects, so 40 enemies means about 440 objects. Destruction that spawns physical rubble runs into the same wall.

Repro

for i=1,200 do
  local o = Scene:CreateObject("S"..i)
  o.pos = Vec3(i%40, 2, i//40)
  o:AddComponent("VoxelData").syncToClients = true
  Vox:Add(Sphere(o.pos,0.3)):Force(o):Run()
end  -- watch Time.fps for 4 s

Suggested fix

Queue object creation behind a per-frame budget, as the edit guard already does for voxel volume, or warn when one frame creates more than N objects. A lightweight "rig part" object type that shares one stream would make segmented characters affordable.

B3

A client loses collision the server still has

CriticalWhy: inferred
Who
A connected player standing on terrain that the server rebuilds while they are there.
What
The player fell through a floor that existed on the server. The client's collision and raycasts missed static voxels that the server reported as present.
When
After a large async Vox:Remove (box quarters), followed within a few frames by Vox:Add in the same region. Building in fresh regions never triggered it.
Where
Client static voxel streaming and collision (VVCollision). The client-side character controller collides against client voxel data only.
Why
The remove and add deltas likely arrive or apply out of order, or the add is dropped while the remove is still streaming. None of AE:ReloadGeometry(), AE:AEVV_InvalidateData() or Client:ReloadPage(false) repaired it. ReloadPage did nothing at all in the native client.

Impact

Any destructible or rebuildable world, which is the platform's headline feature, can drop players into the void. I worked around it with settle waits after clears and a fall-catch that teleports players back.

Repro

Vox:Remove(Box(c, Vec3(16,4,16))):ForceStatic():Run()
util:schedule(0.05, function()
  Vox:Add(Cylinder(c, c+Vec3(0,1,0), 7)):ForceStatic():Run()
end)  -- stand a client on c

Suggested fix

Order or version static deltas per chunk so a client never applies an older remove over a newer add. Expose a working "resync region" call. Make ReloadPage work in the native client, or report an error when it can't.

B4

Sync overwrites a newer local save

CriticalWhy: measured
Who
Makers and coding agents editing through npx virtualmatter sync.
What
I saved Hollow.lua twice, about 5 s apart. The log shows pushed Hollow.lua and then a run of pulled Hollow.lua. The second local edit was gone from disk, with no conflict file and no warning. Separately, a stopped background sync left its node child running; two syncs then produced .remote-conflict files and pulled a 157 MB .am~ temp file into the mirror.
When
When a local save lands while the hot-reload echo of the previous push is still being pulled back.
Where
The CLI's two-way sync: the echo of its own push is treated as a remote change.
Why
The pull compares the remote copy against stale state instead of the content hash it just pushed, so its own echo overwrites a newer local file.

Impact

This is silent loss of source code. An agent that saves a file twice in a row can believe a fix is live when it isn't. I only caught it because I grepped for the change.

Repro

npx virtualmatter sync &
echo "-- a" >> X.lua; sleep 5
echo "-- b" >> X.lua; sleep 20
tail -2 X.lua   # "-- b" is missing

Suggested fix

Track the hash of each push and ignore the matching echo. Never let a pull overwrite a file whose local mtime is newer than the last push; write a conflict file instead. Kill child processes on exit and exclude *.am~.

B5

Networked tables accept any payload size

HighWhy: measured
Who
Every client of a world whose script writes large values into a util:makeNetworkedTable field.
What
A 16 MB string was written in 94 ms. 64 MB and 256 MB strings were also accepted and delivered. At 256 MB the client's ping rose to 3.57 s, freezing input and replication for every player. It recovered once I cleared the field.
When
On a single write. There is no warning at any size.
Where
Networked table delta replication, server to client.
Why
There is no size cap and no chunking: a large value blocks the reliable channel that carries everything else.

Impact

One careless or hostile script, such as a chat log or inventory dump growing without bound, can lag every player in the session.

Repro

self.net.blob = string.rep("x", 256*1024*1024)
-- watch client ping

Suggested fix

Cap each field (for example 1 MB) and raise a Lua error above it. Send large values on a separate low-priority channel so they can't starve input and transform traffic.

B6

The server Lua heap has no ceiling

HighWhy: measured
Who
Whole sessions. A runaway script can starve the host process that every player shares.
What
The Lua heap grew to 3,072 MB with no limit, taking the process to 21.7 GB. A run-lua call that blocked the main thread ran past the 60 s CLI timeout. After freeing, Lua dropped to 9 MB, but the process stayed roughly 0.3 GB above its earlier footprint. Over the whole session, server memory rose from 6.1 GB to about 19 GB.
When
When a script allocates without bound, or a long synchronous loop runs inside run-lua.
Where
The server Lua VM allocator, and the run-lua bridge, which runs on the main thread.
Why
There is no allocator limit or instruction-count hook in the sandbox. The allocator keeps freed pages, which is normal, but nothing tells a maker how close the host is to its limit.

Impact

A single infinite-append bug can take the world down for everyone, and an agent's long query freezes the simulation while it runs.

Repro

local t = {}
while collectgarbage("count")/1024 < 3072 do
  t[#t+1] = string.rep("A", 1024*1024)
end

Suggested fix

Set a per-world Lua memory limit through lua_setallocf that raises a catchable error. Add an instruction-count hook so run-lua fails cleanly instead of hanging the main thread.

B7

imagine() jobs stall forever, silently

HighWhy: inferred
Who
Makers and agents generating assets.
What
Of 11 concurrent jobs, 5 finished quickly and 6 sat at 0% for over 20 minutes. Some prompts never progressed at all ("shadow creature … horror", "iron staff with hook"); reworded, they finished in about 75 s. No job ever fired an error, timeout or failure callback.
When
With more than 5 concurrent jobs, or with certain prompt content.
Where
The imagine() job queue and its generation backend.
Why
Probably a concurrency limit of 5 that drops or parks overflow jobs instead of queueing them. The prompt stalls look like a content filter rejecting the job without reporting back.

Impact

A preview blockout sits in the world indefinitely. Agents can't tell "slow" from "dead", so they wait or retry and burn credits.

Repro

for i=1,11 do
  imagine("a wooden barrel "..i, Scene:CreateObject("I"..i), {})
end  -- 6 never progress

Suggested fix

Queue extra jobs visibly with a status field, add a failure callback and a timeout, and return the reason when a prompt is rejected.

B8

Hot reload orphans everything in flight

HighWhy: measured
Who
Players in a world that is edited live, plus makers running long builds.
What
Saving any .lua file re-runs every script, and anything async is lost: Vox job queues, util:schedule chains and imagine() callbacks. With 40 NPCs alive, one save dropped the server to 0.39 fps for several seconds, and every NPC instance was orphaned.
When
On every save while sync is running, including saves to scripts unrelated to the running work.
Where
The hot reload path: a full Lua reset and re-instantiation of all scripts.
Why
Reload is global rather than per module, and callbacks keep references to the old instances.

Impact

Live-ops edits hitch every player and can break game state. I had to make the terrain builder resumable through Config and avoid saving during builds.

Repro

util:schedule(30, function() print("fired") end)
-- now save any .lua file
-- "fired" never prints

Suggested fix

Reload only the changed module, and remap or cancel orphaned callbacks with a warning. Provide a hook such as OnBeforeReload so scripts can hand off state.

B9

The documented particle cap isn't enforced

MediumWhy: measured
Who
Players on lower-end clients during heavy effects.
What
The docs say "max 500 particles". The client accepted 500, 2,000 and 8,000 in a single call. Client fps went from about 34–43 to 29.2 at 500, 26.2 at 2,000 (minimum 15.7) and 12.7 at 8,000 (minimum 5.4).
When
Immediately, on the client that spawns them.
Where
Editor Tools/Particles.lua addParticle on the client.
Why
No cap or eviction exists, and the per-particle simulation runs in Lua.

Impact

Effects-heavy moments, such as explosions or a crowd of fire, drop clients into slideshow territory.

Repro

local ps = Scene:GetObjectByName("Particles"):FindScript("Particles")
for i=1,8000 do ps:addParticle(p, {lifetime={5,6}}) end

Suggested fix

Enforce the cap by evicting the oldest particles, and make it configurable. Long term, simulate particles natively or on the GPU.

B10

Scene-wide LOD starvation

MediumWhy: measured
Who
Every client in a scene with many prioritized dynamic objects.
What
About 48 objects with prioritizeLod = true (lodBias 5) collapsed the whole scene's LOD on the client into giant blocks, including the hub fire 7 m from the camera. Removing them restored detail. lodBias 3 per character, without the prioritize flag, was fine.
When
When the combined prioritized budget exceeds the client's stream budget.
Where
The client LOD and streaming budget allocator.
Why
The prioritized objects take the shared budget before the rest of the scene gets any.

Impact

Making characters look sharp silently ruins everything else on screen.

Repro

for each of 48 rig parts:
  vd.prioritizeLod = true; vd.lodBias = 5

Suggested fix

Cap the share of the budget that prioritized objects can claim, and keep a floor for static terrain near the camera.

B11

Transforms that don't replicate

MediumWhy: measured
Who
Makers building attached gear, props or rigs.
What
A child object created on the server with scale 0.089 showed up on clients at scale 1.0, producing a mace 11 times too big. Plain objects without a character controller showed up on clients at (0,0,0).
When
On creation, and on every later change.
Where
Object transform replication.
Why
Only character controllers replicate their position, through RPCs, and scale is never sent. The docs mention position, but the scale case catches people out.

Impact

Every maker ends up building their own transform sync.

Repro

local c = Scene:CreateObject("G"); c.parent = root
c.scale = 0.089   -- client reads 1.0

Suggested fix

Add an opt-in replicateTransform flag that covers position, rotation and scale, or at least send initial values at spawn.

B12

Persisted tables come back opaque

MediumWhy: measured
Who
Anyone persisting game state.
What
Config:TempSet(key, table) comes back as an opaque sol.LuaTable userdata that can't be indexed or iterated. component.varsTable can't be iterated with pairs, and vt.field returns nil for values set with setSerializeVar.
When
On read-back after a Lua reset.
Where
The Config store and the VarTable bindings.
Why
The bindings return the raw sol object rather than converting it back to a Lua table.

Impact

Silent data loss for anyone who doesn't test a round trip. I serialized everything into Lua-literal strings instead.

Repro

Config:TempSet("k", {a=1})
local t = Config:TempGet("k")
return type(t), t.a  -- userdata, error

Suggested fix

Deep-convert values on get, or reject tables on set with a clear error.

B13

Edit guard estimates are hard to predict

MediumWhy: measured
Who
Makers and agents building terrain or structures.
What
A thin cylinder (r 17, h 0.55) was estimated at about 3,195 baseline-m² and rejected, while a sphere of r 6.5 was accepted. A sphere of r 10 was rejected because about 505 m² had already been issued that frame. Single spheres passed up to r 8–11, were soft-rejected at r 12–17 and hard-refused at r 24 and above.
When
On Run().
Where
The Vox edit guard.
Why
Cylinder cost is estimated well above the documented formula, and the guard sums all ops in a frame. The sum is sensible, but the documentation doesn't say so.

Impact

Trial and error for anything larger than a room. The rejection message itself is good and actionable.

Repro

Vox:Add(Cylinder(c, c+Vec3(0,0.55,0), 17))
  :ForceStatic():Run()  -- rejected

Suggested fix

Expose Vox:EstimateCost(op), and document the per-shape cost and the same-frame aggregation.

Editor Tools fail at boot

Docs and runtime disagree

Agents and makers who follow the skills docs.

On first use.
Where
apiEmmyAtomontage.lua and the Skills/ references.

B16

Moving voxel objects plus raycasts spike the server

CriticalWhy: inferred
Who
Every player in a world with server-driven moving characters that also use server raycasts, which describes almost any game with AI.
What
With 24 rigged enemies (6 voxel objects each) moving on the server, 15–27 frames in every 8 s took 50–245 ms, and average fps fell to 40. The game was otherwise identical. Moving the objects without raycasts: 54.9 fps, no spikes. Raycasts without moving: 54.4 fps, no spikes. Both together: the spikes return.
When
When objects are moved through obj.pos at 1–15 Hz while scripts run about 240 static rays per second. The rays use ForceStatic, so they shouldn't touch dynamic objects at all.
Where
Spike frames show NEW/VPO Update Part 7 (80–128 ms), NEW/FixedUpdate VPuzzleObject and NEW/_AmStreaming - Sending (54–74 ms).
Why
Probably a deferred rebuild of the dynamic-object spatial or streaming structures, triggered when a query follows transform changes. An individual ray is only 0.03–1 ms, so the cost lands later in the frame.

Impact

This was the single biggest cause of stutter in the game. The workaround is unusual: keep each enemy's real position in Lua, replicate it through a networked field, and move the engine object only every 10 s or 8 m.

Repro

-- 24 roots with 5 child VoxelData each
-- every frame: root.pos += v*dt
-- 10 Hz each: Cast:Ray(p, down):ForceStatic():Run()
-- watch SUF/Update Frame for 8 s

Suggested fix

Make static-only queries skip dynamic-structure updates. Batch transform-driven rebuilds per frame with a time budget, and expose a "client-driven, server-static" flag for objects whose clients position them anyway (receiveTransform = false).

B17

Fixed per-object cost and very little headroom

HighWhy: measured
Who
Any world with animated characters built from several voxel parts.
What
Each active dynamic VoxelData costs about 21 µs per server frame, even when it doesn't move: 260 rig parts cost 5.4 ms. Inactive objects are effectively free, and switching off 22 hidden template roots saved about 1 ms. editable = false changes nothing. An idle edit session already uses 11.4–12 ms of update time: editor tools Lua is about 1.8 ms (the undo History script alone 0.9 ms), and the server's own screenshot camera adds about 2.6 ms of render and blit. That leaves roughly 4 ms for the game at 60 fps.
When
Constantly.
Where
Update VPuzzleObject and the edit session's Editor Tools.
Why
Per-object bookkeeping runs every frame regardless of state, and editor and screenshot work run even when nobody is using them.

Impact

I cut each enemy from 11 to 5 voxel objects (a lighter rig with virtual elbow and knee joints) to reach 53–56 fps with 24 enemies, up from 13 fps at the start. A solid 60 fps with 24 enemies grouped around one player isn't reachable on this host, because the idle engine overhead alone is about 12 ms.

Repro

-- 260 parked VoxelData objects:
-- SUF/Update Frame goes from 14.7 ms to 20.1 ms

Suggested fix

Skip unchanged objects in the per-frame update. Render the server's screenshot camera only on request. Profile and trim Editor Tools, or turn them off in play sessions.

B18

Clients can't instance voxel assets

MediumWhy: measured
Who
Makers who want animated characters without paying B17 on the server.
What
On the client, AE:GetAssets() returns none of the world's rig assets: 0 of the 150 the server lists. The client VoxelData.data is nil, and a template's .asset reads nil. A client can't create local copies of character parts, so every animated limb has to be a server object.
When
Always.
Where
Client asset sync and VoxelData bindings.
Why
Voxel content is streamed per server object instead of shipped as shared assets.

Impact

It blocks the obvious fix for B17: server keeps one root per character, and each client instances the limbs locally.

Repro

-- on a client
local t = Scene:GetObjectByName("Rig Hollow torso")
return t:GetComponentByType("VoxelData").asset -- nil

Suggested fix

Allow client-local VoxelData to reference a server-streamed object's content, or sync asset references so clients can instance them.

B19

Saving the terrain freezes the server for 33 seconds to over a minute

CriticalWhy: measured
Who
Everyone connected when a world saves its terrain.
What
VoxelData:Save() on the static terrain (a 160 m map at 32 vpm, a 250 MB .am) blocked the main thread past the CLI's 60 s timeout. The CLI returned HTTP 504 and the world was frozen until the save finished. Sync then pulled a 100–120 MB .am~ temp file into the local mirror.

Update: a QA frame sampler happened to straddle one of the Terrain Keeper's automatic saves on an empty server. It recorded a single 33,415 ms frame (10.3 fps averaged over its 8 s window), and every run-lua in that window returned HTTP 504. The same 250 MB map therefore stalls the main thread for anywhere from about 33 s to over 60 s.
When
On every save of the static terrain. Server:SaveScene() also re-saves it.
Where
Static voxel serialization, which is synchronous and saves the whole file every time.
Why
The save is a single blocking write of the entire common collection, with no async, incremental or per-chunk dirty path.

Impact

A persistent survival world can't save its terrain while anyone plays. Most terrain changes are only safe once the server is empty.

Mitigation shipped

A Terrain Keeper module saves the full terrain only after the server has been empty for 45 s, at most every 10 minutes. Between saves, every gameplay edit is written to a compact journal that survives reloads and restarts, and is replayed onto the reverted terrain after a restart. The first automatic save ran while the server was empty. The Keeper now saves edits that the journal doesn't cover at most once an hour.

Suggested fix

Save only dirty chunks, asynchronously on a worker thread with a copy-on-write snapshot. Expose an edit log the engine replays itself.

B20

Gameplay voxel edits aren't persistent by default

HighWhy: measured
Who
Players who dig, salvage, build or destroy, which in a voxel game is everyone.
What
After hours of play the static terrain reported isSaved = false. Only the scene hierarchy had been saved every 2 minutes, which excludes voxels. A restart would revert salvaged walls, burned blight, broken ruins and dug holes. Systems that rebuild from saved game state (homes, blight, arena) would then re-add geometry on top of the reverted terrain. Players see walls that pop back up, and growth that stacks.

Update: dynamic objects lose procedural voxels too. After a server restart, all 12 oil drums (save = true, each built from four Vox:Add cylinders with Force(obj)) were back in the scene, active and with their VoxelData component, but with volume 0, zero bounds and no asset: invisible, with no error. The scene's dynamic-prop count went from 37 to 25.
When
On any server restart.
Where
The split between SaveSceneHierarchy (cheap, no voxels) and voxel saves (B19). It applies to static terrain and to procedurally built dynamic objects; only asset-backed VoxelData, or an explicit VoxelData:Save(), survives.
Why
The cheap save path is the documented default. The voxel save path is too expensive to run while anyone is playing.

Impact

"Persistent world" is the game's promise, and the engine's cheap save path quietly breaks it.

Mitigation shipped

Terrain Keeper journal (see B19). Harvesting, digging, blight burning and lean-to shelters all go through it. Rebuild-from-state systems use exact saved positions, so replaying them is idempotent. For procedural props, the fix is to rebuild on boot whenever the VoxelData is empty, not only when the object is missing, or to save the prop as an asset.

Suggested fix

Include voxel deltas in the hierarchy save (journal or dirty-chunk diffs), or warn makers when a world has gone more than N minutes with unsaved static edits.

B21

The sync overwrite race happened again

HighWhy: measured
Who
Anyone editing through npx virtualmatter sync, especially coding agents that save quickly.
What
Two quick edits to Terrain Keeper.lua: the second was partly lost when sync pulled the echo of the first back over it. One fix was missing from disk with no conflict file. Same mechanism as B4.
When
When two saves to one file land within about 10 s.
Where

AE:GetDebugTime() restarts with the server process

HighWhy: measured
Who
Any game that persists timestamps across server restarts: respawn timers, cooldowns, rate limits, save schedules.
What
The server restarted unexpectedly at about 22:24. Memory was at 13.1 of 32 GB, so it wasn't out of memory, and the cause is unknown. Right afterwards, AE:GetDebugTime() read 79 s: it is process uptime, not wall-clock time. Every timer Ashlight had persisted as "wall clock" was wrong after the restart: the Abbot's 45-minute respawn, the siege's once-an-hour limit, the Omen ward and Abbot-stirs timers, and the Terrain Keeper's save gaps. Game state saved every 2 minutes was reloaded from its last disk save, so a one-shot world repair made just before (re-seating a stacked home) was reverted.
When
On every server process restart, planned or not.
Where
AE:GetDebugTime(); the platform's restart behaviour. The CLI's own agent guide lists AE:GetDebugTime() as "wall clock", next to Time.time (simulation time).
Why
The sandbox removes os.time, and no wall-clock or persistent clock replaces it. The only clocks are simulation time, which restarts on every Lua reload (B27), and process uptime, which restarts with the process.

Impact

Timers that persist across restarts silently fire early, or never, after a restart. With no visible cause and no warning before the restart, the last few minutes of game state are lost, along with any repair made in that window.

Mitigation shipped

A persistent game clock: seconds accumulated in the ledger, plus the uptime since boot, with older timestamps clamped to "now". Downtime doesn't count toward any timer. The ledger is saved to disk immediately after any one-shot repair, and a boot pass re-applies home repairs on its own.

Suggested fix

Expose a real wall-clock time (for example Time.unix), correct the guide's "wall clock" label, and log or announce the reason for every server restart.

B42

Baked rig variants are huge, and a periodic freeze appeared with them

MediumWhy: inferred
Who
Games that bake cosmetic detail into rig assets to avoid runtime voxel cost (B29), their makers' mirrors, and every client that streams the assets.
What
VoxelData:SaveAs on a scaled rig part stores the part at its fine internal resolution, so every baked variant is a full copy. Mace tiers came to about 7 MB each, and the 111 armour and weapon variants to 329 MB of .am assets, all of which sync to the maker's mirror and have to stream to clients. Separately, the patch that switched characters over to the baked armour introduced a freeze of about 700 ms every 8.4 s on an idle server, with the heap growing about 2 MB per freeze and no game Lua running inside it. Reverting that patch fixed it at once (58.2 fps, worst frame 28 ms).
When
When baking variants of scaled parts; the freeze appeared once the baked variants were wired into the character script.
Where
VoxelData:SaveAs on scaled VoxelData; asset handling for large numbers of voxel assets.
Why
The size follows from the scaled part's internal resolution (see B29 and B31). The freeze is under investigation; the suspicion is a periodic engine scan of the asset list that grows with the number of large assets.

Impact

Baking trades a voxel-commit stall for disk, sync and streaming size, and here also for a periodic server-wide freeze. Neither runtime stamping (B29) nor baking is currently a clean way to give characters per-tier detail.

Mitigation

The armour patch was reverted; the baked assets stay on disk so they can be relinked once the freeze is understood. Hollow crusts use only three baked torso variants, which showed no freeze.

Suggested fix

Let SaveAs resample to a target resolution, or support instancing and sharing of voxel data between variants. Keep any periodic asset scan incremental, and expose its cost in the engine timers.

What held up

Recovery

Every test recovered fully after cleanup. Server fps went back to 59.5–59.8, and nothing crashed the host.

Edit guard

Oversized voxel edits were refused before they could stall the frame, with an actionable message.

Raycasts and RPCs

Fast and steady at volumes far beyond what gameplay needs.

Custom rendering

A full-screen light pass rewritten in ssao2.fs hot-reloaded live and carried game state through the fog uniforms.

Persistence

Player homes, fuel levels and quest state survived Lua reloads through a ledger serialized as Lua-literal strings.

Live building

A 160 m map, five segmented character rigs and ten tutorial steps were all built through the CLI without opening the editor.

Runtime voxel detail on characters

Worn armour is stamped as voxels straight into each player's own copies of the rig parts, so it adds no objects. Each plate is an oriented box built from the part's transform at the moment its edit runs, which keeps it correct on a moving character. Verified on a live dummy at tiers 1 and 3. Caveat (B31): measure the live rig; offline mocks got the part scale wrong.

Baking runtime detail into assets

Stamping a template copy once and calling VoxelData:SaveAs stores the stamps in a new asset. Bound copies measured 22–26k voxels against 15.9k plain, so the detail survives, and spawning from the baked variants costs no voxel ops. It is now used live for Hollow crusts. Cosmetic detail on scaled rigs should be baked, not stamped at runtime, but baked variants are large (B42), so keep their number small.

Method

  • Each test ramped load in steps and sampled server fps for 3–5 s after every step. It stopped at the first breach: fps under 20–25, memory over 27 GB, or a Lua error.
  • To separate a creation spike from ongoing cost, I created loads gradually and then measured again at steady state.
  • Causes were isolated with Scene:SetProfileScriptsUpdate plus microbenchmarks timed with AE:GetDebugTime.
  • All test objects were created at least 200 m from play areas and removed afterwards.
  • Organic findings (B3, B7, B8, B10–B15) came up while building the game. Controlled findings (B1, B2, B5, B6, B9) came from the stress harness.
  • Limits: one host, one native client, one session. Client-side numbers depend on the hardware. I did not test multiple concurrent human players.
