Where Virtual Matter Breaks: the move to iteration076

What changed for two live games when the platform moved from engine release/iteration073 to release/iteration076 (76.0.20390, 24d309b4; native client 76.0.1605; CLI 0.6.8). SCAR (destruction FPS) was moved on 2026-10-20 and has been fixed, improved and republished on 076. Ashlight (souls-dark survival) is still on 073; its migration is staged. Same 5W format as the Ashlight and SCAR editions: IDs are M1, M2... and older cards are cited by their B- or F-number. Alongside the breakages, this edition lists what got better, our recommendations, and the questions we would like answered before the next iteration and the new renderer.

Engine iteration076 · 24d309b4 Client Native, Windows, 76.0.1605 SCAR 18QYJ28E5mDi5I1uRKpoY (076) Ashlight 9b9ILBOjInycFrZ0KCFn1 (073) Tooling virtualmatter CLI 0.6.8 + vm-agent-tools Previous editions Ashlight v33 · SCAR final

Executive summary

  1. 076 is much faster. SCAR's client frame went from 42 ms to about 7 ms on the same laptop, particles got ten times cheaper, and the maker felt it at once.
  2. It also broke both games silently. Fields and signatures moved (receiveTransform, PlaySound, AddScript, client ray options) and the new strict setters throw inside the pcall guards that games use, so nothing was logged. SCAR lost its first-person gun and its soldiers lagged; Ashlight would lose its camera, rigs and bosses (M1-M5).
  3. Custom shaders become frozen forks. The engine keeps an edited built-in shader with one warning line, even when its inputs changed. Ashlight's light pass reads the wrong uniform block on 076 (M6).
  4. Terrain edits cost more than before in our test: about 80 ms of server compute and a 55-85 ms frame per dig (M7, F12).
  5. The desktop app leaks the sign-in email as the player name (M8).
  6. The new renderer is not in 076. It is the same AEVV renderer. 076 adds look controls (runtime shader defines, VM Sky, god rays, DOF) but no new rendering path; our questions about it are below.

Findings

M1

receiveTransform moved off VoxelData with no alias; inside pcall the failed write is silent

CriticalWhy: measured↑ index
Who
every world built before 076 that sets engine fields inside pcall (common defensive style, and the platform's own SDK examples did it).
What
receiveTransform moved from VoxelData to Object. On 076 vd.receiveTransform reads nil, and assigning it raises caught (...) exception, because writing an unknown field on an engine object throws (it already did on 073, where the field still existed). Inside pcall nothing is logged.
When
from the first boot on iteration076 (SCAR was moved 2026-10-20 17:12 UTC with no notice to the maker).
Where
engine object property setters (VoxelData, Object); the same rule now applies to Widget:Set{...}, which drops the whole table if one key is unknown.
Why
the API move shipped without an alias or a deprecation warning, and the resulting exception is swallowed by the guard.

Impact

SCAR: the first-person gun and arms vanished (the viewmodel was parked 6 m under the player and streamed back from the server), and every other soldier lagged behind its true position. Ashlight (still on 073): 18 writes, 17 of them unguarded, each of which aborts the enclosing Start/bind: no local camera or controls, no rig assembly, every boss client broken.

Repro

local vd = obj:GetComponentByType('VoxelData'); print(pcall(function() vd.receiveTransform = false end)) -> false on 076, true on 073 (on 073 obj.receiveTransform reads nil).

Mitigation shipped

write obj.receiveTransform; a helper that tries the Object field and falls back to the VoxelData field works on both builds.

Suggested fix

keep a deprecated alias for one iteration that forwards the old field and logs a single warning naming the new location. Log (rate-limited) every unknown-field write even when it is caught.

M2

Audio:PlaySound rejects string paths

HighWhy: measured↑ index
Who
any world that plays sounds by path ('Sounds/Thud02'), a documented 073 idiom.
What
PlaySound / PlaySoundRelative raise expected a AudioFile Asset, got string.
When
076.
Where
Audio API.
Why
signature tightened to Asset handles.

Impact

in SCAR the spawn, grenade-throw, spade-whiff and big-explosion layer cues were silent (their asset names were missing, so code fell back to paths inside pcall).

Repro

Audio:PlaySound('Sounds/Thud02', Vec3(0,0,0), 1, false) on a client.

Mitigation shipped

resolve a path's basename to an Asset through AE:GetAssets() once, cache it.

Suggested fix

accept a path again (resolve it internally), or throw a clear error that is not swallowed: these calls are normally guarded because audio must never crash gameplay.

M3

Object:AddScript needs a LuaFile Asset, not a path

HighWhy: measured↑ index
Who
worlds that attach scripts at runtime, including SCAR's workaround for F27 (published scenes losing script attachments).
What
obj:AddScript('Scar/Scar Mover.lua', true) raises expected a LuaFile Asset, got string.
When
076.
Where
Object:AddScript(luaFile, sync) (073: AddScript(fileName, sync)).
Why
signature change, no overload kept.

Impact

SCAR's boot self-repair for missing scripts would fail silently on a play server, and creating a missing pawn aborted serverStart. Our own recon agent first concluded paths still worked, from a call that had run on 073 code paths; only a live 076 test showed the throw.

Repro

on a 076 server: Scene:CreateObject('t'):AddScript('Scar/Scar Mover.lua', true).

Mitigation shipped

look the Asset up by name and confirm with AE:AssetPathInMontage(asset) == path.

Suggested fix

keep the string overload, or add AE:GetAssetByPath(path) so there is one obvious migration.

M4

Client raycasts lost WithNormal, WithColor and WithMaterial

HighWhy: measured↑ index
Who
any client-side gameplay that reads surfaces: grenade bounces, decals, impact effects, footstep materials.
What
on clients the three options throw (WithNormal() only supported on server), and so does reading hit.normal, hit.color or hit.material (normal/color/material are read by the server raycast only). hit.obj is nil for every client hit. On the server, reading hit.material without WithMaterial() now throws too.
When
076.
Where
Cast/Raycast on the client.
Why
the client copy of static data apparently no longer exposes surface attributes to Lua.

Impact

SCAR on clients: every thrown gadget's local proxy fell through the ground; every bullet impact used the soil palette, with no sparks or ricochets on concrete or steel. Ashlight: the salvage glints and the [E] Salvage prompt (a client WithColor() ray) will disappear on 076.

Repro

client: Cast:Ray(cam.pos, Vec3(0,-5,0)):WithNormal():Run().

Mitigation shipped

plain client rays with an ignore list; the server now sends the impact material with each shot event (one extra RPC argument).

Suggested fix

allow these on clients (the client renders the same voxels), or return nil fields instead of throwing; document it next to F7 (ForceStatic() is also server-only).

M5

The native Sky component is gone; VM Sky, god rays and lens flare switch on

HighWhy: confirmed (component absent on SCAR 076; Ashlight not yet migrated)↑ index
Who
worlds that hid or steered the old sky (Ashlight's dead-sun look).
What
GetComponentByType('Sky') returns nil; the sky is now a Lua SkyObject plus a physical VM Sky. God rays and lens flare (Dev/GodRays, Dev/LensFlare) are on by default.
When
076.
Where
scene sky, Editor Tools/Sky.lua.
Why
sky rewrite.

Impact

Ashlight's pcall-wrapped .render = false and sun settings silently do nothing, so a lit blue or sunset sky and sun shafts would render behind a game built on darkness.

Repro

on 076: Scene:GetObjectsByName('Sky')[1]:GetComponentByType('Sky') -> nil.

Mitigation shipped

Client:SetSkyEnabled(false), Client:SetSunDirection, and the two Dev toggles set to 0 (all pcall'd, harmless on 073).

Suggested fix

a migration note per removed component; a scene-load warning when a script references a removed component type.

M6

A maker-edited shader is kept forever and silently stops matching the renderer's inputs

CriticalWhy: measured (SCAR) and inferred from source (Ashlight)↑ index
Who
every world that customises a built-in shader, the only route to a custom look (SCAR edits vpuzzle2.fs; Ashlight replaces ssao2.fs and patches common.glsl).
What
at boot the engine re-aligns built-in shader copies but keeps edited ones with ... is a maker edit - kept; it may not match this build's inputs (SCAR log: 55 aligned, 1 maker edits kept). The 076 composite ssao2.fs no longer includes common.glsl; it declares its own FogFrame block at AE_BINDING(0) and drops h_viewportSize.
When
every engine move.
Where
Shaders/ alignment (UpdateMontageBasePrefabs).
Why
there is no merge path or stable injection point for custom shading, so an edit becomes a fork.

Impact

SCAR's edit happened to stay compatible (the 076 built-in vpuzzle2.fs equals 073's) but will never receive engine fixes. Ashlight's light pass reads the wrong uniform block on 076: world-position reconstruction, the lantern and the packed game state would be garbage, and the fog-off variant likely fails to compile. The only signal is one log line.

Repro

edit any built-in shader, move the world to a newer iteration, grep the boot log for maker edit - kept.

Mitigation shipped

port by hand: diff the new built-in, re-apply the edit, check Client:GetShaderErrors() (new in 076) on a real client, screenshot.

Suggested fix

a supported hook (custom grade / post-process slot with a stable uniform block), or ship the previous built-in next to each kept edit so a 3-way merge is possible; surface kept edits in the editor UI.

M7

One terrain edit now costs about 80 ms of server compute and a 55-85 ms frame (F12 was 30-50 ms on 073)

HighWhy: measured (2 x 9 digs)↑ index
Who
every world with destructible terrain; it caps how much digging a match can have.
What
9 unbatched digs (capsule r 0.8) on the idle 076 editor server with one client: compute avg 82.0 ms, max 112.5 ms (from OnFinished's computeTimeMs); worst server frame after each edit p50 58.4, p90 67.6, max 85.5 ms. With the new OpBase:Batch(): compute 81.4 ms avg, worst frame p50 54.6, max 84.1 ms. The connected native client never hitched (worst frame 12.7 / 14.4 ms); edits arrived ~0.15 s after the op (unbatched) and ~0.37 s (batched).
When
every static Vox op.
Where
server voxel op commit.
Why
unknown; 073 measured 30-33 ms worst frames for the same dig size (F12). Conditions differ (editor world vs play server), so this needs confirming on a play server.

Impact

at SCAR's budget of 2.5 ops/s the server spends ~20% of its time in edits and drops frames on every dig; hit registration and movement for every player share that thread.

Repro

probes/srv_edit_cost.lua from the SCAR physics work: 6 single digs 1 s apart, then 3 in one frame, with OnFinished timing and a 12-frame worst-frame window.

Mitigation shipped

global edit budget with a frame governor; Batch() kept off for gameplay edits (it delays delivery and saves nothing server-side), on for cosmetic paints.

Suggested fix

move the commit off the main thread (the server multithreading for voxel ops discussed in October); document what Batch() is meant to save.

M8

The desktop app sends the sign-in email address as the player nickname

HighWhy: confirmed↑ index
Who
every maker or player who signs in to the native desktop app with an email.
What
the app launches the client with --nickname <email>; Chat clamps it to 14 characters, so others see name@domai.
When

What

M10

Generated sounds are mostly sub-20 Hz energy and DC offset, so they play quiet

MediumWhy: measured↑ index
Who
anyone using Fal:requestTextToSound for game audio.
What
of 19 takes generated on 2026-10-21, gunshot and whoosh prompts put 83-98% of their energy below 20 Hz, with DC offsets around -39 dB; raw peaks were -23 to -29 dBFS for gunshots. The original SCAR Carbine and Sidearm takes (Oct) were the same: they peaked at -29 / -32 dBFS against +0.3 for another take, which is why the maker's own gun was quieter than distant enemies. Asset names are also re-cased (ScarGen Carbine 2b -> Scargen Carbine 2B).
When
text-to-sound workflow.
Where
generator output (no DC block or loudness normalisation).
Why
generator artifact.

Impact

an untreated take plays 10-20 dB quieter than the built-in sounds next to it, and only a thin crack is heard (see M11).

Repro

generate 'close-up assault rifle single gunshot', run ffmpeg -af volumedetect and an FFT on the mp3.

Mitigation shipped

40 Hz high-pass, presence EQ, compression and limiting to about -9 LUFS, then push the mp3 under the final name.

Suggested fix

DC-block, high-pass and loudness-normalise generator output (for example to -14 LUFS, peak -1 dBFS); return mono for one-shots.

M11

Engine audio output removes everything below ~150 Hz and tracks loudness, not peak

MediumWhy: measured (loopback capture)↑ index
Who
sound design for any world.
What
capturing the native client's output and comparing bands with the source: below 100 Hz -47 to -50 dB, 100-200 Hz -18 to -24 dB, mids -8 to -17 dB. Two files with the same peak and RMS played 5 dB apart, matching their integrated loudness (-14.1 vs -9.0 LUFS). Setting src.volume = 4 raised output only 4.3 dB. Mono and stereo files of the same content played at the same level.
When

Where
mixer / output stage.
Why
unknown (a master high-pass and limiter would explain it).

Impact

bass-heavy sounds (explosions, gunshots, footsteps) lose their weight; level matching by peak or RMS is misleading.

Repro

play two takes with equal peak but different spectra through PlaySoundRelative and record the system output.

Mitigation shipped

author for the mids, match on LUFS.

Suggested fix

document the output chain; expose per-source filters and bus volumes (there is no low-pass, so distance muffling has to be faked with pitch).

M14

Camera zNear resets after AddComponent('Camera')

LowWhy: measured↑ index

A near plane of 0.05 written right after adding the camera reads back as 0.1 later; writes made afterwards stick. The first-person gun clipped through the near plane until SCAR re-asserted 0.05 each frame when it drifted above 0.06.

M15

Push conflicts on files whose content did not change

LowWhy: confirmed↑ index

After boot the engine rewrites aligned shader copies, which changes their etags. Pushing an edited Shaders/vpuzzle2.fs then reported a conflict although the world copy was byte-identical to our base. fetch of that one file followed by a normal push resolved it. Suggested fix: compare content before declaring a conflict.

M16

A connected client keeps playing the old decoding of a replaced sound

LowWhy: measured↑ index

Pushing a new file under an existing sound name updates the asset (server and client report the new size), but a client that already played it keeps the old audio until it reloads. A/B tests need fresh asset names. Suggested fix: invalidate the decoded buffer when the asset's file changes.

M17

LowWhy: observed↑ index

Dev/Fog/Density above 0 blacks out the new sky (screenshot gfx-l-fog.png). Fog is also the only data channel Ashlight has into its light pass, which is why it must keep the sky off. Setting a Dev key that did not exist also creates it permanently.

M18

LowWhy: observed↑ index

What got better

Client frame time 42 -> 7 ms

Native client, Intel Iris Xe, 1080p, SCAR at Medium: 6.7-7.9 ms per frame on 076 against 42 ms (12 ms of it shadows) on 073. The maker noticed it as soon as they played.

Particles 10x cheaper

About 4-6 µs per live particle (200 add 1.16 ms) against about 50 µs on 073; billboards about 2.4 µs. SCAR raised its effect budgets.

Runtime shader defines

Client:SetVPuzzleShaderDefines switches stylised lighting, posterisation and saturation per client without forking a shader. It is the first supported look control.

Client:GetShaderErrors()

Shader compile errors are finally visible from Lua; we used it to verify SCAR's grade on a real client.

VM Sky, sun and live DOF

SetSkyLook, SetSunDirection, god rays, lens flare and a working depth of field (it contradicts the platform's own shaders guide, which says post effects are not wired).

Edit queue API

Vox.editQueue, OpBase:Batch(), Vox:flushEdits() and an OnFinished(info, computeTimeMs, status) callback make edit cost measurable from Lua for the first time.

Richer RigidBody

Writable velocity and angularVelocity, sleeping, impulses, forces and torques. SCAR's debris now settles and sleeps instead of fighting the terrain.

Reusable rays

Mutating a cached Raycast's startPos costs 0.060 ms against 0.100 ms for a fresh ray with a 160-object ignore list.

Shader alignment

Unedited built-in shader copies are refreshed automatically at boot (55 of SCAR's 56).

CLI 0.6.8

push, fetch, status, publish and logs --restarts replaced most of our custom tooling; the restart log explains every stop.

SCAR on 076: what we shipped

Five specialist agents (audio, API, graphics, physics, first-person feel) audited SCAR on 076 against the live editor and a connected native client; one lead composed their 93 anchored patches and deployed them on 2026-10-21, then republished the play server. Measured results:

  • First-person gun: back (M1) and steady on rock (M9). A damped eye spring cut camera jolt over measured rocky ground from 88 to 24 m/s² at 60 fps.
  • Reloads: per-weapon animation with a visible magazine, keyed to new mag-out, mag-in and bolt sounds; no aiming during a magazine reload.
  • Own-gun loudness: was -47 dB against -25 dB for a distant enemy Marksman. New generated takes (M10) loudness-matched to the engine's best built-in rifle; remote guns roll off properly and gain a distant boom.
  • Other soldiers: rig roots stop taking server transforms; interpolation delay 0.205 -> 0.17 s, without overshoot (a 5 m/s runner no longer renders at 8.8 m/s).
  • Ragdolls: fixed a frame-rate bug (deaths played 2.4x fast at 144 fps), a mid-air freeze off-screen and a wall launch.
  • Effects: impacts get their real surface again via the server (M4); particle budgets raised on the strength of 076's cheaper particles.
  • Privacy: lobby names no longer show part of an email (M8); 36 guest records and the email-named record were cleaned from the save data.

Concept: "Ashlight, drawn in ember and ink"

Ashlight's economy is fuel, light and safety. The concept makes that the art direction: inside a light radius the world is rendered in warm, banded toon light; outside it the world is only sketched in cold ink lines on soot. Fuel literally draws the world. What 076 already allows, and what we would want from the new renderer:

  • Banded lantern light. Quantise each light's falloff into 3-4 hard bands in the light pass, matched to the server's safety thresholds, so players see the exact edge of safety. Voxel side: CUSTOM_LIGHTING_MODE 0 plus LIGHTPOSTER through SetVPuzzleShaderDefines, set once at join.
  • Ink in the dark. A depth-edge line in the same pass (the edge term is already computed), soot-black in light and faint slate outside it, so ruins and the Hollow read against the void without being lit. Boss tells as coloured VoxelData.outline (amber parry window, cold blue unblockable).
  • Embers as the brightest thing on screen. Everything else posterised; embers, Emberheart cracks and beacon coals stay smooth with a small halo, so the eye goes to fuel.
  • Layered darkness. Distance haze in three stepped bands; Dread raises the band count, the Dimming collapses it to one.
  • The dead sun, with god rays used once. VM Sky stays off; the Great Lantern tier-up and the Siege dawn get a scripted 8-second "sun breaks through" with Dev/GodRays.

Risks we would like the renderer team's view on: a hand-written pass can be invalidated by the new renderer exactly as M6 describes; SetVPuzzleShaderDefines is labelled experimental and recompiles every effect (~100 ms); outline cost is unknown; and the maker playtests in a browser, where a posterised full-screen pass is unmeasured.

Recommendations

  1. Deprecate before removing. Keep moved fields and old signatures (paths in PlaySound and AddScript) working for one iteration with a one-time warning that names the replacement. Three of SCAR's four breaks would have been log lines instead of invisible bugs (M1-M4).
  2. Log caught engine errors. A rate-limited log of exceptions raised inside pcall by engine setters would have found every 076 break on the first boot.
  3. Publish a breaking-change list per iteration and notify makers before moving a world; let them pin, opt in, or test on a copy (M12).
  4. Give custom shading a stable home. A grade or post-process slot with a documented uniform block, or at least the previous built-in kept beside each edited copy, so edits can be merged instead of frozen (M6). This matters most before the new renderer lands.
  5. Profile the static edit commit. It is the core cost of every destructible game and seems to have grown on 076 (M7).
  6. Fix the nickname. Never pass the sign-in email to worlds (M8).
  7. Clean generator audio (DC block, high-pass, loudness normalisation) and document the client's output chain (M10, M11).
  8. Render after LateUpdate or document the order (M9); allow surface rays on clients (M4).
  9. CLI: warn when publish would send a stale InitScene (M13); do not report a conflict when content is unchanged (M15); show the engine iteration in status.

Questions for future iterations

The new renderer

  1. Which iteration ships the "entirely new renderer" shown on LinkedIn (cel-shaded microvoxels), and will it be per-world opt-in?076 still boots the AEVV renderer with the same voxel shader as 073; we found no new renderer code path, define or API.
  2. What happens to worlds with edited vpuzzle2.fs / ssao2.fs / common.glsl under it?Both games depend on edits that the current alignment keeps as frozen forks (M6). We would rather plan the port than discover it.
  3. Is the cel look a renderer feature, a set of SetVPuzzleShaderDefines options, or a shader recipe the built-in agent writes?The post says "just ask the built-in agent". Coding agents working through the CLI are told never to drive that agent, so we need the underlying API.
  4. Will stylisation be per object (toon bands, ink outlines on character rigs) or only global?Ashlight's concept uses light as ink: banded light inside lantern radii, ink edges in the dark, outline-coded boss tells via VoxelData.outline.
  5. Will point lights light voxels?Ashlight bakes arena light positions into its shader and packs game state into fog uniforms because there is no other way to light voxels from gameplay.
  6. What do microvoxels change for collision, client ray precision (F5: 0.125-0.5 m quantisation) and edit cost (M7)?Finer voxels could make digging better or much more expensive.
  7. How does the new renderer perform in browser (WASM) clients?Our makers playtest in Chrome; 076's native gains (42 -> 7 ms) are measured only on the desktop app.

Engine iterations

  1. Will makers get notice and a changelog before their worlds move, and can a world be pinned or tested on a copy first?See M12. SCAR broke silently; Ashlight is still on 073 and needs a planned move.
  2. Can old engine objects keep deprecated aliases for one iteration?See M1-M3.
  3. Is the FogFrame uniform block the stable interface for composite-pass shaders, and is there a supported way to pass custom uniforms to a post pass?Ashlight currently smuggles game state through Dev/Fog/* as exact integers below 2^24.
  4. Is the server-side voxel multithreading still planned, and in which iteration?It is the fix for M7 and F12.
  5. Why are surface attributes no longer readable from client rays?If it is a deliberate security or memory choice, documenting it would save every maker a debugging session (M4).

Audio and platform

  1. Is there a master high-pass or limiter on the client, and will per-source filters or buses come?See M11. Distance muffling and music ducking are not possible today.
  2. Can text-to-sound output be normalised?See M10.
  3. Can the desktop app keep more than one engine build, so makers can open older worlds?Installing the 076 client removed the 073 one.

Where Virtual Matter Breaks: the move to iteration076

What changed for two live games when the platform moved from engine release/iteration073 to release/iteration076 (76.0.20390, 24d309b4; native client 76.0.1605; CLI 0.6.8). SCAR (destruction FPS) was moved on 2026-10-20 and has been fixed, improved and republished on 076. Ashlight (souls-dark survival) is still on 073; its migration is staged. Same 5W format as the Ashlight and SCAR editions: IDs are M1, M2... and older cards are cited by their B- or F-number. Alongside the breakages, this edition lists what got better, our recommendations, and the questions we would like answered before the next iteration and the new renderer.

Engine iteration076 · 24d309b4 Client Native, Windows, 76.0.1605 SCAR 18QYJ28E5mDi5I1uRKpoY (076) Ashlight 9b9ILBOjInycFrZ0KCFn1 (073) Tooling virtualmatter CLI 0.6.8 + vm-agent-tools Previous editions Ashlight v33 · SCAR final

Executive summary

  1. 076 is much faster. SCAR's client frame went from 42 ms to about 7 ms on the same laptop, particles got ten times cheaper, and the maker felt it at once.
  2. It also broke both games silently. Fields and signatures moved (receiveTransform, PlaySound, AddScript, client ray options) and the new strict setters throw inside the pcall guards that games use, so nothing was logged. SCAR lost its first-person gun and its soldiers lagged; Ashlight would lose its camera, rigs and bosses (M1-M5).
  3. Custom shaders become frozen forks. The engine keeps an edited built-in shader with one warning line, even when its inputs changed. Ashlight's light pass reads the wrong uniform block on 076 (M6).
  4. Terrain edits cost more than before in our test: about 80 ms of server compute and a 55-85 ms frame per dig (M7, F12).
  5. The desktop app leaks the sign-in email as the player name (M8).
  6. The new renderer is not in 076. It is the same AEVV renderer. 076 adds look controls (runtime shader defines, VM Sky, god rays, DOF) but no new rendering path; our questions about it are below.

Findings

M1

receiveTransform moved off VoxelData with no alias; inside pcall the failed write is silent

CriticalWhy: measured↑ index
Who
every world built before 076 that sets engine fields inside pcall (common defensive style, and the platform's own SDK examples did it).
What
receiveTransform moved from VoxelData to Object. On 076 vd.receiveTransform reads nil, and assigning it raises caught (...) exception, because writing an unknown field on an engine object throws (it already did on 073, where the field still existed). Inside pcall nothing is logged.
When
from the first boot on iteration076 (SCAR was moved 2026-10-20 17:12 UTC with no notice to the maker).
Where
engine object property setters (VoxelData, Object); the same rule now applies to Widget:Set{...}, which drops the whole table if one key is unknown.
Why
the API move shipped without an alias or a deprecation warning, and the resulting exception is swallowed by the guard.

Impact

SCAR: the first-person gun and arms vanished (the viewmodel was parked 6 m under the player and streamed back from the server), and every other soldier lagged behind its true position. Ashlight (still on 073): 18 writes, 17 of them unguarded, each of which aborts the enclosing Start/bind: no local camera or controls, no rig assembly, every boss client broken.

Repro

local vd = obj:GetComponentByType('VoxelData'); print(pcall(function() vd.receiveTransform = false end)) -> false on 076, true on 073 (on 073 obj.receiveTransform reads nil).

Mitigation shipped

write obj.receiveTransform; a helper that tries the Object field and falls back to the VoxelData field works on both builds.

Suggested fix

keep a deprecated alias for one iteration that forwards the old field and logs a single warning naming the new location. Log (rate-limited) every unknown-field write even when it is caught.

Audio:PlaySound rejects string paths

HighWhy: measured↑ index
Who
any world that plays sounds by path ('Sounds/Thud02'), a documented 073 idiom.
What
PlaySound / PlaySoundRelative raise expected a AudioFile Asset, got string.
When
076.
Where
Audio API.
Why
signature tightened to Asset handles.

Impact

in SCAR the spawn, grenade-throw, spade-whiff and big-explosion layer cues were silent (their asset names were missing, so code fell back to paths inside pcall).

Repro

Mitigation shipped

resolve a path's basename to an Asset through AE:GetAssets() once, cache it.

accept a path again (resolve it internally), or throw a clear error that is not swallowed: these calls are normally guarded because audio must never crash gameplay.

worlds that attach scripts at runtime, including SCAR's workaround for F27 (published scenes losing script attachments).

M4

Client raycasts lost WithNormal, WithColor and WithMaterial

HighWhy: measured↑ index
Who
any client-side gameplay that reads surfaces: grenade bounces, decals, impact effects, footstep materials.
What
on clients the three options throw (WithNormal() only supported on server), and so does reading hit.normal, hit.color or hit.material (normal/color/material are read by the server raycast only). hit.obj is nil for every client hit. On the server, reading hit.material without WithMaterial() now throws too.
When

Where
Cast/Raycast on the client.
Why
the client copy of static data apparently no longer exposes surface attributes to Lua.

Impact

SCAR on clients: every thrown gadget's local proxy fell through the ground; every bullet impact used the soil palette, with no sparks or ricochets on concrete or steel. Ashlight: the salvage glints and the [E] Salvage prompt (a client WithColor() ray) will disappear on 076.

Repro

client: Cast:Ray(cam.pos, Vec3(0,-5,0)):WithNormal():Run().

Mitigation shipped

plain client rays with an ignore list; the server now sends the impact material with each shot event (one extra RPC argument).

Suggested fix

allow these on clients (the client renders the same voxels), or return nil fields instead of throwing; document it next to F7 (ForceStatic() is also server-only).

M6

A maker-edited shader is kept forever and silently stops matching the renderer's inputs

CriticalWhy: measured (SCAR) and inferred from source (Ashlight)↑ index
Who
every world that customises a built-in shader, the only route to a custom look (SCAR edits vpuzzle2.fs; Ashlight replaces ssao2.fs and patches common.glsl).
What
at boot the engine re-aligns built-in shader copies but keeps edited ones with ... is a maker edit - kept; it may not match this build's inputs (SCAR log: 55 aligned, 1 maker edits kept). every engine move.

Shaders/ alignment (UpdateMontageBasePrefabs).

SCAR's edit happened to stay compatible (the 076 built-in vpuzzle2.fs equals 073's) but will never receive engine fixes. M7

One terrain edit now costs about 80 ms of server compute and a 55-85 ms frame (F12 was 30-50 ms on 073)

HighWhy: measured (2 x 9 digs)↑ index
Who
every world with destructible terrain; it caps how much digging a match can have.
What
9 unbatched digs (capsule r 0.8) on the idle 076 editor server with one client: compute avg 82.0 ms, max 112.5 ms (from OnFinished's computeTimeMs); worst server frame after each edit p50 58.4, p90 67.6, max 85.5 ms. When
every static Vox op.
Where
server voxel op commit.
Why
unknown; 073 measured 30-33 ms worst frames for the same dig size (F12). Conditions differ (editor world vs play server), so this needs confirming on a play server.

Impact

at SCAR's budget of 2.5 ops/s the server spends ~20% of its time in edits and drops frames on every dig; hit registration and movement for every player share that thread.

Repro

global edit budget with a frame governor; Batch() kept off for gameplay edits (it delays delivery and saves nothing server-side), on for cosmetic paints.

Suggested fix

move the commit off the main thread (the server multithreading for voxel ops discussed in October); document what Batch() is meant to save.

What got better

Client frame time 42 -> 7 ms

Native client, Intel Iris Xe, 1080p, SCAR at Medium: 6.7-7.9 ms per frame on 076 against 42 ms (12 ms of it shadows) on 073. The maker noticed it as soon as they played.

Particles 10x cheaper

About 4-6 µs per live particle (200 add 1.16 ms) against about 50 µs on 073; billboards about 2.4 µs. SCAR raised its effect budgets.

Runtime shader defines

Client:SetVPuzzleShaderDefines switches stylised lighting, posterisation and saturation per client without forking a shader. It is the first supported look control.

Client:GetShaderErrors()

Shader compile errors are finally visible from Lua; we used it to verify SCAR's grade on a real client.

VM Sky, sun and live DOF

SetSkyLook, SetSunDirection, god rays, lens flare and a working depth of field (it contradicts the platform's own shaders guide, which says post effects are not wired).

Edit queue API

Vox.editQueue, OpBase:Batch(), Vox:flushEdits() and an OnFinished(info, computeTimeMs, status) callback make edit cost measurable from Lua for the first time.

Richer RigidBody

Writable velocity and angularVelocity, sleeping, impulses, forces and torques. SCAR's debris now settles and sleeps instead of fighting the terrain.

Reusable rays

Mutating a cached Raycast's startPos costs 0.060 ms against 0.100 ms for a fresh ray with a 160-object ignore list.

Shader alignment

Unedited built-in shader copies are refreshed automatically at boot (55 of SCAR's 56).

CLI 0.6.8

push, fetch, status, publish and logs --restarts replaced most of our custom tooling; the restart log explains every stop.

SCAR on 076: what we shipped

Five specialist agents (audio, API, graphics, physics, first-person feel) audited SCAR on 076 against the live editor and a connected native client; one lead composed their 93 anchored patches and deployed them on 2026-10-21, then republished the play server. Measured results:

  • First-person gun: back (M1) and steady on rock (M9). A damped eye spring cut camera jolt over measured rocky ground from 88 to 24 m/s² at 60 fps.
  • Reloads: per-weapon animation with a visible magazine, keyed to new mag-out, mag-in and bolt sounds; no aiming during a magazine reload.
  • Own-gun loudness: was -47 dB against -25 dB for a distant enemy Marksman. New generated takes (M10) loudness-matched to the engine's best built-in rifle; remote guns roll off properly and gain a distant boom.
  • Other soldiers: rig roots stop taking server transforms; interpolation delay 0.205 -> 0.17 s, without overshoot (a 5 m/s runner no longer renders at 8.8 m/s).
  • Ragdolls: fixed a frame-rate bug (deaths played 2.4x fast at 144 fps), a mid-air freeze off-screen and a wall launch.
  • Effects: impacts get their real surface again via the server (M4); particle budgets raised on the strength of 076's cheaper particles.

Concept: "Ashlight, drawn in ember and ink"

Ashlight's economy is fuel, light and safety. The concept makes that the art direction: inside a light radius the world is rendered in warm, banded toon light; outside it the world is only sketched in cold ink lines on soot. Fuel literally draws the world. What 076 already allows, and what we would want from the new renderer:

  • Banded lantern light. Quantise each light's falloff into 3-4 hard bands in the light pass, matched to the server's safety thresholds, so players see the exact edge of safety. Voxel side: CUSTOM_LIGHTING_MODE 0 plus LIGHTPOSTER through SetVPuzzleShaderDefines, set once at join.
  • Ink in the dark. A depth-edge line in the same pass (the edge term is already computed), soot-black in light and faint slate outside it, so ruins and the Hollow read against the void without being lit. Boss tells as coloured VoxelData.outline (amber parry window, cold blue unblockable).
  • Embers as the brightest thing on screen. Everything else posterised; embers, Emberheart cracks and beacon coals stay smooth with a small halo, so the eye goes to fuel.
  • Layered darkness. Distance haze in three stepped bands; Dread raises the band count, the Dimming collapses it to one.
  • The dead sun, with god rays used once. VM Sky stays off; the Great Lantern tier-up and the Siege dawn get a scripted 8-second "sun breaks through" with Dev/GodRays.

Risks we would like the renderer team's view on: a hand-written pass can be invalidated by the new renderer exactly as M6 describes; SetVPuzzleShaderDefines is labelled experimental and recompiles every effect (~100 ms); outline cost is unknown; and the maker playtests in a browser, where a posterised full-screen pass is unmeasured.

Recommendations

  1. Deprecate before removing. Keep moved fields and old signatures (paths in PlaySound and AddScript) working for one iteration with a one-time warning that names the replacement. Three of SCAR's four breaks would have been log lines instead of invisible bugs (M1-M4).
  2. Log caught engine errors. A rate-limited log of exceptions raised inside pcall by engine setters would have found every 076 break on the first boot.
  3. Publish a breaking-change list per iteration and notify makers before moving a world; let them pin, opt in, or test on a copy (M12).
  4. Give custom shading a stable home. A grade or post-process slot with a documented uniform block, or at least the previous built-in kept beside each edited copy, so edits can be merged instead of frozen (M6). This matters most before the new renderer lands.
  5. Profile the static edit commit. It is the core cost of every destructible game and seems to have grown on 076 (M7).
  6. Fix the nickname. Never pass the sign-in email to worlds (M8).
  7. Clean generator audio (DC block, high-pass, loudness normalisation) and document the client's output chain (M10, M11).
  8. Render after LateUpdate or document the order (M9); allow surface rays on clients (M4).
  9. CLI: warn when publish would send a stale InitScene (M13); do not report a conflict when content is unchanged (M15); show the engine iteration in status.

Questions for future iterations

The new renderer

  1. Which iteration ships the "entirely new renderer" shown on LinkedIn (cel-shaded microvoxels), and will it be per-world opt-in?076 still boots the AEVV renderer with the same voxel shader as 073; we found no new renderer code path, define or API.
  2. What happens to worlds with edited vpuzzle2.fs / ssao2.fs / common.glsl under it?Both games depend on edits that the current alignment keeps as frozen forks (M6). We would rather plan the port than discover it.
  3. Is the cel look a renderer feature, a set of SetVPuzzleShaderDefines options, or a shader recipe the built-in agent writes?The post says "just ask the built-in agent". Coding agents working through the CLI are told never to drive that agent, so we need the underlying API.
  4. Will stylisation be per object (toon bands, ink outlines on character rigs) or only global?Ashlight's concept uses light as ink: banded light inside lantern radii, ink edges in the dark, outline-coded boss tells via VoxelData.outline.
  5. Will point lights light voxels?Ashlight bakes arena light positions into its shader and packs game state into fog uniforms because there is no other way to light voxels from gameplay.
  6. What do microvoxels change for collision, client ray precision (F5: 0.125-0.5 m quantisation) and edit cost (M7)?Finer voxels could make digging better or much more expensive.
  7. How does the new renderer perform in browser (WASM) clients?Our makers playtest in Chrome; 076's native gains (42 -> 7 ms) are measured only on the desktop app.

Engine iterations

  1. Will makers get notice and a changelog before their worlds move, and can a world be pinned or tested on a copy first?See M12. SCAR broke silently; Ashlight is still on 073 and needs a planned move.
  2. Can old engine objects keep deprecated aliases for one iteration?See M1-M3.
  3. Is the FogFrame uniform block the stable interface for composite-pass shaders, and is there a supported way to pass custom uniforms to a post pass?Ashlight currently smuggles game state through Dev/Fog/* as exact integers below 2^24.
  4. Is the server-side voxel multithreading still planned, and in which iteration?It is the fix for M7 and F12.
  5. Why are surface attributes no longer readable from client rays?If it is a deliberate security or memory choice, documenting it would save every maker a debugging session (M4).

Audio and platform

  1. Is there a master high-pass or limiter on the client, and will per-source filters or buses come?See M11. Distance muffling and music ducking are not possible today.
  2. Can text-to-sound output be normalised?See M10.
  3. Can the desktop app keep more than one engine build, so makers can open older worlds?Installing the 076 client removed the 073 one.
